# Fact 7.6(4): constrained filtration-25 E5 quotient

This directory connects the two existing Fact 7.6(4) obstructions to the complete
three-coordinate E4 center used by `Stem125E5Search`. The result is conditional
on actual algebraic meanings, complete source/target coordinates, both incoming
columns, and a genuine outgoing-zero (or named-cycle plus complex) premise.
It does not prove a permanent cycle or identify a topological Adams page.

## Exact coordinates

At `(21,147)` the E2 basis IDs are `[3748,3749,3750]`. The checked d2/d3
projections give `(x1,x0)`. Staircase row 3749 has base `1` and is the first
E4 source; staircase row 3750 has base `0` and is the second. Staircase row
3748 has base `2` and becomes an earlier boundary. In particular, staircase
3750 is basis3748, not basis3750. The d3 source comparison uses the previously
explicit conditional row3564 and other full-column premises.

At `(25,150)` the E2 basis IDs are `[3992,3993,3994,3995]`. Its d2 cycle law is
`x0=x1`, the d2 projection is `(x3,x2,x1)`, and the d3 projection is the identity.
Basis3994 is monomial `[13,13,13,13,51]`. SQL names generator13 as `g` and
generator51 as `Delta h_1g`; hence the raw named vector is `e2` and its E4
vector is `e1`. Staircase3993, not staircase3994, records this named vector.
Generator names and the topological identification still need mathematical
interpretation; an SQL string is not such a proof.

The known staircase3749 differential gives incoming column `e0`. The product
and map obstructions, together with the d2 cycle equation, force the unknown
raw column to `(1,1,1,b)`, which becomes `(b,1,1)` in E4. Both possible values
of `b` are retained. The older `E4Descent` coordinate order is connected by an
explicit permutation theorem; it is not silently reused as the aggregate order.

## What the theorems establish

- `Coordinates.lean` proves every source/target coordinate equation, raw cycle
  condition, named representative, and older-quotient permutation.
- `Conclusion.lean` reuses `combined_affine` and the whole-space
  `UniqueHomologyCertificates` checker. With full outgoing zero, branches 8/18
  have a one-dimensional entire cycle/boundary quotient generated by `e1`.
  The quantifier covers every cycle, not only named rows.
- `Obstructions.lean` derives the compatibility conditions from true product
  and naturality equations. `ProductMeaning` requires the factor cycle,
  known product differential, Leibniz equation, all relation evaluations, and
  reflection of actual zero into the earlier-boundary image. `MapMeaning`
  requires the ring map, every checked substitution column's actual meaning,
  naturality, the mapped-source zero, and the analogous boundary reflection.
  These are explicit hypotheses; no proof-log reason supplies them.
  The two meanings are sufficient algebraic arguments about the same candidate,
  but may use different source elements and different differential contexts.
  This interface does not prove that they belong to one actual Adams system.
- `Imported.lean` imports the two C++ JSON certificates and rechecks them with
  `unique_homology_cert`, and proves batch validity.

The obstructions alone select indices **8,9,18,19**, not only 8/18. The full
matrix `[0,1,1]` is a valid outgoing differential for either constrained
incoming matrix. In indices9/19 the named `e1` is not a cycle and the E5
quotient is zero-dimensional. `counterexample` proves this in Lean. Thus a
product with `h1`, or either obstruction, must not be treated as a proof of
named survival. If the actual named element is a d4 cycle, the complex law
and the two incoming columns force the full outgoing matrix to zero; this
alternative hypothesis is proved sufficient by `unique_from_named_cycle`.

## Import and batch interface

`export.py` invokes the existing C++ `UniqueHomologyCertificates/unique-export`
for both requests and checks that batch and individual output bytes agree.
`requests.txt`, `certificate0.json`, `certificate1.json`, and
`certificates.jsonl` are reproducible outputs. JSON uses version1, canonical
field order, complete matrices, a full homology comparison, and the named
vector. Hashes record identity only; the Lean checker verifies the mathematics.

```lean
import Fact764ConstrainedE5.Imported
open Fact764ConstrainedE5 Fact764ConstrainedE5.Conclusion
open Fact764ConstrainedE5.Coordinates UniqueHomologyCertificates

example : IsUniqueNonzeroClass outgoing (incoming false) named := by
  unique_homology_cert using Imported.certificate0
```

The generic CLI `UniqueHomologyCertificates/CheckFile.lean` accepts the JSONL
batch and reports file/line plus comparison, dimension, named-cycle, canonical
JSON, unknown-field, or duplicate-field failures. `test_import.py` checks two
valid records and eight meaningful mutations, including the nonzero outgoing
counterexample, lost incoming column, named boundary, and corrupted projection.

## Reproduction and audit

From the repository root, with the existing C++ producer built:

```text
python3 program/Fact764ConstrainedE5/export.py
python3 program/Fact764ConstrainedE5/compile.py
python3 program/Fact764ConstrainedE5/review.py
python3 program/Fact764ConstrainedE5/test_import.py
python3 program/Fact764ConstrainedE5/assert_current.py
```

Direct compilation is serial `lean -j1`, using the configured Lean4.32.2
toolchain and prebuilt project dependencies. The four modules report 18
standard-only axiom dependencies: `propext`, `Classical.choice`, `Quot.sound`.
There are no admitted proofs, custom axioms, or native-evaluation trust.

The arithmetic review independently reads the source database and checks all
16 raw candidates, 512 full outgoing/incoming matrix pairs, the exact 20 complex
branches, both whole-quotient identities, and 128 cycle-pair equivalences. It
preserves the original 358 aggregate blocks. The saved build hashes describe
actual direct runs; a later Lake build may replace oleans and should be recorded
as a separate build checkpoint rather than rewriting earlier run evidence.
